## Обзор

В этом каталоге содержатся Architecture Decision Records (ADR) для AutoDev Marketplace MVP.

ADR документируют важные архитектурные решения, их контекст, последствия и альтернативы.

---

## Структура ADR

Каждый ADR имеет следующую структуру:

```markdown
# ADR-X: Название решения

**Дата:** YYYY-MM-DD  
**Статус:** proposed | approved | rejected | deprecated | superseded

---

## Контекст

Описание проблемы и контекста.

## Решение

Описание выбранного решения.

## Последствия

Плюсы и минусы решения.

## Альтернативы

Рассмотренные альтернативы и почему они были отклонены.
```

## Детали ADR

### ADR-0001: Консолидация 25+ микросервисов в 8 для MVP

**Дата:** 2026-06-04  
**Статус:** Approved

---

#### Контекст

Изначально проект планировался с 25+ микросервисами, что является избыточным для стартового проекта (MVP):
- Каждый сервис требует отдельного разработчика
- Трассировка через 10+ сервисов крайне сложна
- Оверхед в управлении требует сложной оркестрации
- Проблемы с транзакциями через 10+ сервисов
- Каждый сервис требует отдельной БД/экземпляра

#### Решение

Сконсолидировать микросервисы в 8 сервисов для MVP:

| Сервис | Состав |
|--------|--------|
| api-gateway | Входящий трафик |
| auth-service | Аутентификация |
| catalog-service | Products + Prices + Availability |
| order-service | Orders + Delivery + Returns |
| search-service | Поиск |
| payment-service | Оплата |
| communication-service | Notifications + Messaging |
| platform-service | Users + Moderation + Reviews + Analytics + Admin |

#### Последствия

**Плюсы:**
- ✅ -68% меньше сервисов (25+ → 8)
- ✅ -50% сложность отладки
- ✅ -50% сложность оркестрации
- ✅ -68% меньше разработчиков (25+ → 8)
- ✅ Ускоренный MVP-релиз (до 3 месяцев)
- ✅ Легче в отладке и мониторинге

**Минусы:**
- ⚠️ Изоляция сбоев снижается (средняя)
- ⚠️ Каждый сервис может быть больше

#### Альтернативы

1. **Оставить 25+ сервисов** — отклонено из-за высокой сложности для MVP
2. **Консолидировать в 12 сервисов** — отклонено как промежуточный вариант
3. **Минимизировать до 6 сервисов** — отклонено как слишком упрощённо

### ADR-0002: Использование Spring Boot 3.x для микросервисов

**Дата:** 2026-06-04  
**Статус:** Approved

#### Контекст

Проект должен быть учебным и использовать современные технологии Java.

#### Решение

Использовать Spring Boot 3.4.5 с Java 17.

#### Последствия

**Плюсы:**
- ✅ Современный стек технологий
- ✅ Поддержка Java 17 (LTS)
- ✅ Упрощённая конфигурация
- ✅ Большая экосистема

**Минусы:**
- ⚠️ Требует Java 17+

#### Альтернативы

- Spring Boot 2.x — отклонено как устаревшее
- Micronaut — отклонено из-за меньшей популярности
- Quarkus — отклонено из-за меньшей популярности

### ADR-0003: Выбор PostgreSQL для хранения данных

**Дата:** 2026-06-04  
**Статус:** Approved

#### Контекст

Требуется надёжная реляционная СУБД для хранения структурированных данных.

#### Решение

Использовать PostgreSQL 15.

#### Последствия

**Плюсы:**
- ✅ Надёжность и ACID-совместимость
- ✅ Поддержка JSONB для гибких данных
- ✅ Хорошая производительность
- ✅ Большая экосистема

**Минусы:**
- ⚠️ Требуется настройка для горизонтального масштабирования

#### Альтернативы

- MySQL — отклонено как менее функциональное
- Oracle — отклонено из-за лицензирования
- MongoDB — отклонено как нереляционная

Использовать Apache Kafka 7.3.2.

**Плюсы:**
- ✅ Высокая производительность

- ✅ Event Sourcing поддержка

- Redis Streams — отклонено как менее надёжный
- Pulsar — отклонено как менее популярный
