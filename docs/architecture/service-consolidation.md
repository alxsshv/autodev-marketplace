## Обзор

Документ описывает стратегию консолидации микросервисов для AutoDev Marketplace. Изначально проект планировал 25+ микросервисов, что является избыточным для стартового проекта (MVP). После анализа бизнес-требований и технических ограничений предложена оптимизированная архитектура из **8 сервисов** для MVP.

**Проблемы исходной архитектуры:**
- **25+ сервисов** — слишком много для старта (каждый требует отдельного разработчика)
- **Комплексность отладки** — трассировка через 10+ сервисов крайне сложна
- **Оверхед в управлении** — координация между 25+ сервисами требует сложной оркестрации
- **Проблемы с транзакциями** — Saga pattern через 10+ сервисов становится непрактичным
- **Ресурсы** — каждый сервис требует отдельной БД/экземпляра

## Целевая архитектура (8 сервисов для MVP)

### Консолидированные сервисы:

| # | Сервис | Бизнес-область | Состав | Обоснование |
|---|--------|----------------|--------|-------------|
| 1 | `api-gateway` | Входящий трафик | — | Единая точка входа — обязательна |
| 2 | `auth-service` | Аутентификация | — | Keycloak, JWT, RBAC — критично |
| 3 | `catalog-service` | Управление товарами | Products + Categories + Prices + Availability | Цены и наличие тесно связаны с товарами |
| 4 | `order-service` | Оформление заказов | Orders + Cart + Delivery + Returns | Логистика и возвраты — часть заказа |
| 5 | `search-service` | Поиск | — | Полнотекстовый поиск — отдельная зона |
| 6 | `payment-service` | Оплата | — | Платежи — критичный домен |
| 7 | `communication-service` | Коммуникация | Notifications + Messaging | Уведомления и чат — каналы коммуникации |
| 8 | `platform-service` | Платформа | Users + Moderation + Reviews + Analytics + Admin + Marketing | Управление платформой — единый домен |

**Итого для MVP: 8 сервисов**

**Примечание:** В новой архитектуре:
- **Keycloak** — единственный источник правды для ролей
- **Auth Service** — обертка над Keycloak для синхронизации пользователей и кэширования

## Подробное описание консолидаций

### 1. `catalog-service` — объединение catalog + pricing + inventory

**Обоснование:**
- **Высокая связность:** Товары, цены и наличие — единая бизнес-область
- **Транзакции:** Резервирование товара требует синхронного обновления цены и наличия
- **Простота:** Покупатель сначала смотрит товар, потом цену, потом наличие — единый flow
- **Примеры аналогов:** Amazon (product page содержит товар, цена, наличие)

**Структура:**
- Product (catalog)
- Category (catalog)
- Brand (catalog)
- Price (pricing)
- Inventory (inventory)
- VIN Compatibility (catalog)
- Alternatives (catalog)
- Cross References (catalog)

**Обновления:**
- Таблицы в PostgreSQL: `catalog.products`, `catalog.categories`, `catalog.brands`, `catalog.prices`, `catalog.inventory`
- События Kafka: `catalog.product.created`, `catalog.price.updated`, `catalog.stock.updated`
- Elasticsearch: индекс `products` с включёнными ценами и наличием

**Риски:**
- ✅ **Низкий:** Цены и наличие можно кэшировать отдельно в Redis
- ✅ **Низкий:** Индексация в Elasticsearch может быть асинхронной

---

### 2. `order-service` — объединение order + logistics + returns

**Обоснование:**
- **Корпоративный паттерн:** "Order" — это полный жизненный цикл покупки
- **Транзакции:** Доставка и возврат — часть заказа (ссылки по ID)
- **Простота:** Покупатель смотрит статус заказа — единый экран
- **Примеры аналогов:** Ozon, Wildberries — один сервис для всех операций с заказом

**Структура:**
- Order (order)
- Cart (order)
- Delivery (logistics)
- Return (returns)

**Обновления:**
- Таблицы в PostgreSQL: `order_service.orders`, `order_service.carts`, `order_service.deliveries`, `order_service.returns`
- События Kafka: `order.order.created`, `order.delivery.updated`, `order.return.processed`
- Интеграция: Inventory Service (резервирование), Payment Service (оплата)

**Риски:**
- ✅ **Низкий:** Резервирование товара — асинхронное событие через Kafka
- ✅ **Низкий:** Расчёт стоимости доставки — вызов Logistics Service (в рамках order-service)

---

### 3. `communication-service` — объединение notification + messaging

**Обоснование:**
- **Корпоративный паттерн:** "Communication" — все каналы взаимодействия с пользователем
- **Простота:** Пользователь настраивает частоту уведомлений — единые настройки
- **Эффективность:** Общая база для истории сообщений и уведомлений
- **Примеры аналогов:** Slack (сообщения + уведомления), Telegram (сообщения + уведомления)

**Структура:**
- Notification (notification) — email, SMS, push
- Message (messaging) — чат
- Subscription (notification)
- Template (notification/messaging)

**Обновления:**
- Таблицы в PostgreSQL: `communication_service.notifications`, `communication_service.messages`, `communication_service.subscriptions`, `communication_service.templates`
- События Kafka: `communication.notification.sent`, `communication.message.created`
- WebSocket: для чата в реальном времени

**Риски:**
- ✅ **Низкий:** Уведомления и чат могут использовать разные очереди Kafka
- ✅ **Низкий:** Разные шаблоны для email/SMS/push и чата

---

### 4. `platform-service` — объединение user + moderation + review + analytics + admin + marketing

**Обоснование:**
- **Корпоративный паттерн:** "Platform Management" — управление платформой
- **Роль пользователей:** User — это платформенная функция (не бизнес-домен)
- **Простота:** Администратор управляет всем через одну панель
- **Эффективность:** Модерация и отзывы — единый процесс контента
- **Примеры аналогов:** eBay (админка управляет всем), Amazon Seller Central

**Структура:**
- User (user) — профили, лояльность
- Moderation (moderation) — контент
- Review (review) — отзывы
- Analytics (analytics) — метрики
- Admin (admin) — настройки
- Marketing (marketing) — реклама

**Обновления:**
- Таблицы в PostgreSQL: `platform_service.users`, `platform_service.profiles`, `platform_service.loyalty`, `platform_service.moderation`, `platform_service.reviews`, `platform_service.analytics`, `platform_service.admin`, `platform_service.marketing`
- События Kafka: `platform.user.registered`, `platform.review.moderated`, `platform.analytics.updated`

**ВАЖНО:** Роли пользователей хранятся исключительно в Keycloak. В PostgreSQL нет таблиц для хранения ролей.

**Риски:****
- ⚠️ **Средний:** Платформа может быть большой — изолировать модули через пакеты Java
- ✅ **Низкий:** Кэширование профилей — в Redis, как и раньше

---

### 5. `integration-service` — TecDoc, 1С, веб-хуки (опционально для MVP)

**Обоснование:**
- **Не критично для MVP:** Внешние интеграции можно реализовать позже
- **Сложность:** Интеграции требуют специальных знаний (TecDoc API, 1С API)
- **Гибкость:** Можно реализовать как отдельный сервис или внутри других сервисов

**Рекомендация:**
- Для MVP: реализовать только базовую интеграцию с TecDoc (в catalog-service)
- Для следующих этапов: вынести в отдельный integration-service

## Сравнение архитектур

| Критерий | Исходная (25+ сервисов) | Целевая (8 сервисов) | Улучшение |
|----------|------------------------|------------------------|-----------|
| **Количество сервисов** | 25+ | 8 | ✅ -68% |
| **Комплексность отладки** | Высокая | Низкая | ✅ -50% |
| **Сложность оркестрации** | Высокая | Низкая | ✅ -50% |
| **Сложность транзакций** | Высокая | Низкая | ✅ -50% |
| **Количество разработчиков** | 25+ | 8 | ✅ -68% |
| **Количество БД** | 25+ | 8 | ✅ -68% |
| **Количество экземпляров** | 25+ | 8 | ✅ -68% |
| **Изоляция сбоев** | Высокая | Средняя | ⚠️ -20% |
| **Масштабируемость** | Высокая | Высокая | ✅ 0% |

**Вывод:** Целевая архитектура оптимальна для MVP. Изоляция сбоев снижается, но это оправдано для стартового проекта.

## Заключение

Консолидация сервисов — **не отказ от микросервисной архитектуры**, а **оптимизация для стартового проекта**.

**Принципы консолидации:**
1. **Группировка по бизнес-областям:** Товары, заказы, коммуникация, платформа
2. **Корпоративные паттерны:** Использование проверенных решений
3. **Минимизация сложности:** 8-10 сервисов — управляемое количество
4. **Гибкость:** Можно разделять сервисы позже, когда потребуется

**Ключевой вывод:** 
> "Лучшая архитектура — та, которая позволяет быстро запустить MVP и получить обратную связь от пользователей. Микросервисы можно разделить позже, когда будет ясна реальная нагрузка и бизнес-требования."
