### Что должен описать архитектор в файле overview для системы продажи автозапчастей

Файл `overview` (обзор архитектуры) — стартовый документ для команды, стейкхолдеров и новых участников проекта. Он даёт целостное представление о системе без погружения в детали реализации.

#### 1. Видение и цели системы

* **Бизнес‑цели:** кратко описать, какую проблему решает система и какую ценность несёт (например, «создать распределённую платформу для продажи автозапчастей с функционалом, аналогичным Drom.ru»).
* **Целевая аудитория:** кто будет использовать систему (покупатели, продавцы, модераторы, администраторы).
* **Ключевые бизнес‑ценности:** например, удобство поиска запчастей, безопасная сделка, автоматизация загрузки прайс‑листов.
* **Ограничения и допущения:** например, «система должна поддерживать загрузку прайс‑листов в форматах CSV, XLSX, XML».

#### 2. Контекст системы

* **Взаимодействие с внешними системами:** перечислить внешние сервисы и интерфейсы (платёжные шлюзы, службы доставки, CRM, ERP, каталоги запчастей типа TecDoc).
* **Границы системы:** что входит в scope проекта, а что — нет (например, мобильное приложение может разрабатываться отдельно).
* **Стейкхолдеры:** кто заинтересован в системе (владельцы бизнеса, продавцы, покупатели, служба поддержки, ИТ‑команда).

#### 3. Архитектурные представления

Использовать нотации (например, C4 Model) для разных уровней детализации:

* **Context (уровень 1):** высокоуровневый взгляд на систему в окружении пользователей и внешних систем (диаграмма в стиле C4 Context).
* **Container (уровень 2):** основные контейнеры (веб‑приложение, бэкенд‑сервисы, БД, кэш, брокеры сообщений) и их технологии (Java, Spring Boot, PostgreSQL, Redis, Kafka).
* **Component (уровень 3):** ключевые компоненты внутри контейнеров (например, `UserService`, `ProductCatalogService`, `OrderService`, `PricingService`).
* **Код (уровень 4):** примеры ключевых классов или интерфейсов (опционально, может быть в отдельных документах).

#### 4. Технологический стек

Структурированный список технологий с версиями:

* **Бэкенд:** Java 17+, Spring Boot 3.x, Spring WebFlux (если применимо), Spring Security.
* **Сборка и управление зависимостями:** Gradle 8.x.
* **База данных:** PostgreSQL 15+ (основная), Redis 7+ (кэш).
* **Очереди сообщений:** Apache Kafka 3.x или RabbitMQ 3.x.
* **Поиск:** Elasticsearch 8.x (для быстрого поиска и фильтрации запчастей).
* **Контейнеризация:** Docker 24.x.
* **Оркестрация:** Kubernetes 1.28+ (для микросервисов).
* **Мониторинг:** Prometheus, Grafana, Spring Boot Actuator.
* **Логирование:** ELK Stack (Elasticsearch, Logstash, Kibana) или Graylog.
* **CI/CD:** GitLab CI/CD или Jenkins.

#### 5. Ключевые архитектурные решения и принципы

Обосновать выбор архитектуры и технологий:
* **Стиль архитектуры:** микросервисы или монолит (с обоснованием).
* **Коммуникация между сервисами:** REST API, gRPC, асинхронная (через Kafka/RabbitMQ).
* **Паттерны проектирования:** CQRS, Saga (для распределённых транзакций), API Gateway, Service Discovery.
* **Стратегия развёртывания:** Blue‑Green, Canary.
* **Подход к масштабированию:** горизонтальное масштабирование stateless‑сервисов.
* **Управление конфигурацией:** Spring Cloud Config или внешние системы (HashiCorp Vault).

#### 6. Основные функциональные модули

Краткий перечень и назначение ключевых сервисов/модулей:
* `User Service` — управление пользователями, аутентификация, авторизация.
* `Product Catalog Service` — каталог товаров, категории, характеристики, поиск по VIN.
* `Pricing & Inventory Service` — цены, наличие, загрузка и обновление прайс‑листов.
* `Order Service` — оформление заказов, статусы, безопасная сделка.
* `Notification Service` — отправка email, SMS, push‑уведомлений.
* `Messaging Service` — чат между покупателем и продавцом.
* `Analytics & Reporting Service` — аналитика продаж, дашборды для продавцов.
* `Admin Service` — модерация объявлений, управление контентом, мониторинг.

#### 7. Нефункциональные требования (NFR)

Количественные и качественные характеристики:
* **Производительность:** время отклика API (< 500 мс), пропускная способность (1000 RPS).
* **Надёжность:** доступность 99,9 %, автоматическое восстановление после сбоев.
* **Масштабируемость:** поддержка роста числа пользователей и товаров в 10 раз без переработки архитектуры.
* **Безопасность:** шифрование данных (TLS 1.3), хранение паролей (BCrypt), защита от OWASP Top 10.
* **Отказоустойчивость:** резервирование БД, репликация данных, graceful degradation.
* **Локализация:** поддержка русского и английского языков.

#### 8. Данные и хранение

* **Основные сущности:** `User`, `Product`, `Category`, `Order`, `Seller`, `Review`, `PriceList`.
* **Типы БД:** реляционная (PostgreSQL для транзакционных данных), NoSQL (Redis для кэша, Elasticsearch для поиска).
* **Стратегии репликации и шардирования:** если применимо.
* **Резервное копирование и восстановление:** расписание бэкапов, RPO/RTO.

#### 9. Интеграции

* **Внешние платёжные системы:** Сбербанк, Тинькофф, Stripe (если есть международная аудитория).
* **Службы доставки:** СДЭК, Boxberry, Почта России (API для расчёта стоимости и отслеживания).
* **Каталоги запчастей:** TecDoc (для кросс‑номеров и совместимости).
* **CRM/ERP:** 1С, Bitrix24 (синхронизация данных о заказах и клиентах).
* **Аналитика:** Яндекс.Метрика, Google Analytics.

#### 10. Развёртывание и инфраструктура

* **Окружения:** dev, test, staging, production.
* **Инфраструктура:** облачный провайдер (Yandex Cloud, AWS, Azure) или on‑premise.
* **Сетевая топология:** балансировщики нагрузки, DMZ, firewall rules.
* **Автоматизация развёртывания:** Helm charts для Kubernetes, Terraform для инфраструктуры.

#### 11. Операционные аспекты

* **Мониторинг и алертинг:** метрики (CPU, память, latency), логирование, трассировка (Spring Cloud Sleuth + Zipkin).
* **Обновление и патчи:** стратегия zero‑downtime deployments.
* **Аудит и соответствие:** GDPR, 152‑ФЗ (защита персональных данных).

#### 12. Риски и зависимости

* **Технические риски:** зависимость от внешних API (TecDoc, платёжные шлюзы), сложность интеграции с legacy‑системами продавцов.
* **Операционные риски:** высокая нагрузка в пиковые сезоны, DDoS‑атаки.
* **Митигация:** резервные каналы, кэширование, rate limiting, circuit breaker.

#### 13. Глоссарий и соглашения

* **Термины:** VIN, OEM‑номер, кросс‑номер, эскроу‑счёт, B2B, B2C.
* **Соглашения по именованию:** Java/Spring Boot conventions (package naming, class naming).
* **Версионирование API:** семантическое версионирование (v1, v2), поддержка обратной совместимости.
