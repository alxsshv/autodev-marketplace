## 1. Общее описание

**Auth Service** — централизованный микросервис, обеспечивающий аутентификацию и авторизацию пользователей платформы AutoDev Marketplace. Он реализует OAuth2/OpenID Connect через Keycloak, управление JWT-токенами, и предоставляет API для проверки прав доступа.

**JWT Token Service** — критичный компонент Auth Service, отвечающий за:
- Генерацию JWT токенов (access token 15 мин, refresh token 7 дней) с алгоритмом RS256
- Валидацию токенов (подпись, claims, срок действия)
- Обновление пары токенов через refresh token (одноразовый)
- Отзыв токенов через Redis (revoked tokens)
- Кэширование публичного ключа Keycloak для ускорения валидации (TTL: 1 час)
- Кэширование результатов проверки отозванных токенов (TTL: 1 минута) для производительности

**Типичный сценарий использования:**
1. Пользователь входит через `POST /api/v1/auth/login`.
2. JWT Token Service генерирует пару `access_token` (JWT, 15 мин) и `refresh_token` (JWT, 7 дней, одноразовый).
3. API Gateway валидирует каждый запрос, вызывая `GET /api/v1/auth/validate-token`.
4. При выходе или истечении срока действия токенов — токены инвалидируются и хранятся в Redis.
5. При обновлении токенов через `POST /api/v1/auth/refresh` — старый refresh token помечается как использованный.

## 2. Уточнённые бизнес-требования (по результатам уточнения)

| Вопрос | Решение | Обоснование |
|--------|---------|-------------|
| **Keycloak** | Внешний Keycloak (автономная инстанция) | Для масштабируемости, безопасности и поддержки нескольких клиентов (web, mobile, B2B). |
| **Refresh-токены** | «Одно использование» (одноразовые) | Повышение безопасности: даже при утечке refresh-токена он не может быть использован повторно. |
| **Redis** | Использовать для отозванных/использованных токенов | Для реализации механизма «одно использование» и удержания списков отозванных токенов. |

## 3. Функциональные требования (FR)

### FR-0. JWT Token Service (Генерация и валидация)

| Код | Требование | Детали |
|-----|------------|--------|
| FR-0.1 | Генерация access token | Генерировать JWT с алгоритмом **RS256**, срок жизни **15 минут**, обязательные claims: `sub` (email), `roles`, `iat`, `exp`, `aud`, `iss`. |
| FR-0.2 | Генерация refresh token | Генерировать JWT с алгоритмом **RS256**, срок жизни **7 дней**, обязательные claims: `sub` (email), `jti` (unique id), `iat`, `exp`, `aud`, `iss`. |
| FR-0.3 | Валидация access token | Проверять подпись RS256, неистёкший `exp`, валидный `aud`, `iss`, наличие `roles`. |
| FR-0.4 | Валидация refresh token | Проверять подпись RS256, неистёкший `exp`, наличие в Redis **не как использованный** (`used_refresh:{jti} NOT EXISTS`). |
| FR-0.5 | Хранение в Redis | Добавлять `revoked:access:{hash}` (15 мин) и `revoked:refresh:{hash}` (7 дней) при отзыве. |
| FR-0.6 | Refresh логика | При обновлении токенов: инвалидировать старый refresh token, генерировать новую пару, сохранять новый refresh token как неиспользованный. |
| FR-0.7 | Кэширование публичного ключа Keycloak | При недоступности Keycloak: |
|     | | • Кэшировать публичный ключ для валидации RS256 подписи (TTL: 1 час) |
|     | | • Кэшировать ТОЛЬКО сумму успешных валидаций (не токены!) для fallback (TTL: 5 минут) |
|     | | • Если кэш пуст — возвращать `503 Service Unavailable` (не принимать отозванные токены) |

### FR-1. Аутентификация (Authentication)

| Код | Требование | Детали |
|-----|------------|--------|
| FR-1.1 | `POST /api/v1/auth/login` | Вход по логину/паролю. Возвращает пару `access_token`, `refresh_token`. |
| FR-1.2 | Валидация учётных данных через Keycloak | Использовать OpenID Connect `grant_type=password` (или `grant_type=client_credentials` если через service account), либо напрямую вызывать Admin API Keycloak для верификации. |
| FR-1.3 | Ошибки | `401 Unauthorized` при неверных данных; `429 Too Many Requests` при превышении лимита попыток (5 попыток за 5 минут). |
| FR-1.4 | Учётные данные | Логин — email, пароль — неограниченной сложности (обязательно `BCrypt` на уровне Keycloak). |

### FR-2. Токены и сессии

| Код | Требование | Детали |
|-----|------------|--------|
| FR-2.1 | Генерация пары токенов | Генерировать **access_token** и **refresh_token** как JWT с алгоритмом подписи **RS256**. Access token: **15 минут TTL**, refresh token: **7 дней TTL**. Обязательные claims: `sub` (email), `roles` (массив), `iat` (timestamp), `exp` (timestamp), `aud` (client_id), `iss` (issuer URL). |
| FR-2.2 | `POST /api/v1/auth/refresh` | Обновление пары токенов по валидному `refresh_token`. **После использования `refresh_token` он должен быть помечен как использованный в Redis через `SETNX` (SET if Not eXists) для предотвращения повторного использования.** |
| FR-2.3 | Отзыв токенов | Реализовать `POST /api/v1/auth/logout`, который: |
|     | | • Инвалидирует `access_token` (добавляет `revoked:access:{hash}` в Redis с TTL 15 мин) |
|     | | • Инвалидирует `refresh_token` (добавляет `revoked:refresh:{hash}` в Redis с TTL 7 дней) |
|     | | • Удаляет `used_refresh:{jti}` из Redis (если был) |
| FR-2.4 | Проверка токенов | `GET /api/v1/auth/validate-token` — endpoint, вызываемый API Gateway. Возвращает `200 OK`, если токен валиден, не отозван и не использован. |
| FR-2.5 | Алгоритм JWT | Подписи через **RS256**. Валидация токена: проверка подписи публичным ключом Keycloak, наличие `exp`, `iat`, `roles`, `aud`, `iss`. Отказаться от JWT без любого из обязательных claimов. |
| FR-2.6 | Проверка отозванных токенов | При каждой валидации токена: |
|     | | • Извлечь `token_hash` (SHA-256) из JWT |
|     | | • Проверить Redis на наличие `revoked:access:{token_hash}` |
|     | | • Если токен отозван — вернуть `401 Unauthorized` |
|     | | • Если нет — проверить подпись RS256 и claims |
|     | | • Кэшировать результат проверки revoked в Redis (`cache:revoked_check:{hash}`) TTL: 1 минута |
| FR-2.7 | Redis структура | Использовать следующие ключи Redis: |
|     | | • `revoked:access:{token_hash}` (String, 15 мин TTL) |
|     | | • `revoked:refresh:{token_hash}` (String, 7 дней TTL) |
|     | | • `used_refresh:{jti}` (String, 7 дней TTL, SETNX для уникальности) |
|     | | • `cache:revoked_check:{hash}` (String, 1 мин TTL) |
|     | | • `cache:public_key` (String, 1 час TTL, публичный ключ Keycloak для RS256) |
|     | | • `cache:validation_summary:{hash}` (String, 5 мин TTL, сумма успешных валидаций для fallback) |

### FR-8. Rate Limiting (для MVP)

| Код | Требование | Детали |
|-----|------------|--------|
| FR-8.1 | Лимит попыток входа | Для `/api/v1/auth/login`: **5 попыток за 5 минут** на IP-адрес. Использовать Redis `SETNX` для счётчика `rate:login:{ip}:{5min_window}` |
| FR-8.2 | Лимит привязки провайдеров | Для `/api/v1/auth/external/link`: **3 попытки за 10 минут** на пользователя. Использовать Redis `SETNX` для счётчика `rate:link:{user_id}:{10min_window}` |
| FR-8.3 | Лимит админ-операций | Для `/api/v1/admin/**`: **10 попыток за 1 минуту** на пользователя. Использовать Redis `SETNX` для счётчика `rate:admin:{user_id}:{1min_window}` |
| FR-8.4 | Возврат 429 | При превышении лимита возвращать `429 Too Many Requests` с JSON: `{ "error": "RateLimitExceeded", "message": "Too many requests", "retry_after": 123 }` |
| FR-8.5 | Аудит rate limiting | Логировать `RATE_LIMIT_EXCEEDED` в `auth.audit_logs` с IP, user_id, endpoint, timestamp |
| FR-8.6 | Redis структура | Использовать ключи: `rate:login:{ip}:{window}`, `rate:link:{user_id}:{window}`, `rate:admin:{user_id}:{window}` со сроком жизни TTL = window size |

## 5. Интеграции

### 5.1. Внешние зависимости

| Компонент | Тип | Данные | Ответственность |
|-----------|-----|--------|-----------------|
| **Keycloak** | REST API (Admin API), OIDC, Events API | `User`, `Role`, `Group`, `Events` | Keycloak админ |
| **Redis** | NoSQL (кэш, отозванные токены) | `token_hash → TTL` (15 мин/7 дней) | Auth Service |
| **Kafka** | Мессенджер | `auth.user_authenticated`, `auth.user_logout`, `keycloak.events` (опционально) | Auth Service |
| **Kafka Connect Keycloak Source Connector** | Опционально | События Keycloak (`LOGIN`, `LOGOUT`, `REGISTER`) | DevOps (для полного аудита) |

### 5.2. Контракт с API Gateway

| Параметр | Значение |
|----------|----------|
| `validate-token` endpoint | `GET /api/v1/auth/validate-token?token=<jwt>` |
| Заголовок | `Authorization: Bearer <jwt>` |
| Возвращаемое значение | `200 OK` (если токен валиден и не отозван в Redis), `401 Unauthorized` (если невалиден/отозван) |

### 5.3. Контракт с Keycloak

| Endpoint | Метод | Описание |
|----------|-------|----------|
| `/{realm}/protocol/openid-connect/token` | `POST` | Получение токена (где `realm = autodev`) |
| `/{realm}/protocol/openid-connect/userinfo` | `GET` | Информация о пользователе |
| `/{realm}/admin/realms/{realm}/users` | `GET/POST` | Управление пользователями (Admin API) |
| `/.well-known/openid-configuration` | `GET` | Конфигурация OIDC, публичный ключ |

## 7. Структура данных

### 7.1. Redis-структура (обязательно)

| Ключ | Тип | Значение | TTL | Назначение |
|------|-----|----------|-----|------------|
| `revoked:access:{token_hash}` | String (bool) | `1` | 15 мин | Отзыв access token |
| `revoked:refresh:{token_hash}` | String (bool) | `1` | 7 дней | Отзыв refresh token |
| `used_refresh:{jti}` | String (bool) | `1` | 7 дней | Одноразовый refresh token (SETNX) |
| `cache:revoked_check:{hash}` | String (bool) | `1` мин | Кэш результатов проверки revoked |
| `cache:public_key` | String | Публичный ключ Keycloak | 1 час | Для валидации RS256 подписи |
| `rate:login:{ip}:{5min_window}` | String (count) | Счётчик попыток входа | 5 мин | Rate limiting входа |
| `rate:link:{user_id}:{10min_window}` | String (count) | Счётчик привязки | 10 мин | Rate limiting привязки провайдера |
| `rate:admin:{user_id}:{1min_window}` | String (count) | Счётчик админ-запросов | 1 мин | Rate limiting админ-операций |
| `processed_event:{event_id}` | String (bool) | `1` | 1 час | Идемпотентность Keycloak Events |

**Ключевые особенности:**
- `jti` (JWT ID) — уникальный идентификатор refresh token, используется для предотвращения повторного использования
- `token_hash` — SHA-256 хэш JWT токена (base64 encoded)
- `rate:login:{ip}:{window}` — счётчик для rate limiting входа по IP-адресу, TTL = window size
- `rate:link:{user_id}:{window}` — счётчик для rate limiting привязки провайдера по user_id, TTL = window size
- `rate:admin:{user_id}:{window}` — счётчик для rate limiting админ-операций по user_id, TTL = window size
- Все ключи автоматически удаляются после TTL через Redis EXPIRE

## 8. API-Specific

### 8.1. JWT Claim спецификация

#### Access Token Claims:
```json
{
  "sub": "user@example.com",
  "roles": ["BUYER", "SELLER"],
  "iat": 1712220000,
  "exp": 1712220900,
  "aud": "autodev-gateway",
  "iss": "https://keycloak.autodev.local/realms/autodev"
}
```

#### Refresh Token Claims:
```json
{
  "sub": "user@example.com",
  "jti": "uuid-unique-id",
  "iat": 1712220000,
  "exp": 1712824800,
  "aud": "autodev-gateway",
  "iss": "https://keycloak.autodev.local/realms/autodev"
}
```

#### Валидация токена:
| Claim | Обязательный | Проверка |
|-------|-------------|----------|
| `sub` | Да | Email пользователя (строка) |
| `roles` | Да | Массив строк (BUYER, SELLER, MODERATOR, ADMIN) |
| `iat` | Да | Timestamp (в прошлом, не более 5 мин назад) |
| `exp` | Да | Timestamp (не истёк) |
| `aud` | Да | `autodev-gateway` или `autodev-web` |
| `iss` | Да | `https://keycloak.autodev.local/realms/autodev` |
| `signature` | Да | RS256, валидация публичным ключом Keycloak |

## 11. Критерии приёмки (Acceptance Criteria)

### User Story: «Вход пользователя»

> **AC-1.** `POST /api/v1/auth/login` с правильными логином и паролем возвращает `200 OK` с `access_token` (JWT, 15 мин TTL) и `refresh_token` (JWT, 7 дней TTL).
> **AC-2.** `POST /api/v1/auth/login` с неверным паролем возвращает `401 Unauthorized`.
> **AC-3.** `POST /api/v1/auth/login` с 6-й попыткой за 5 минут возвращает `429 Too Many Requests`.
> **AC-4.** `GET /api/v1/auth/validate-token` возвращает `200 OK` для валидного токена и `401 Unauthorized` для отозванного/невалидного.
> **AC-5.** При отсутствии Keycloak сервис кэширует успешную аутентификацию (TTL: 5 мин) и не возвращает `503`.
> **AC-6.** `POST /api/v1/auth/refresh` с использованным `refresh_token` возвращает `409 Conflict` (уже использован).
> **AC-7.** `POST /api/v1/auth/logout` помечает `access_token` и `refresh_token` как отозванные в Redis (TTL 15 мин / 7 дней).
> **AC-8.** `GET /api/v1/auth/me` возвращает `200 OK` с правильным `user_id` и `roles`.
> **AC-9.** JWT токены содержат обязательные claims: `sub`, `roles`, `iat`, `exp`, `aud`, `iss`.
> **AC-10.** Проверка JWT включает: RS256 подпись, неистёкший `exp`, валидный `iss`, наличие `roles`.
> **AC-11.** Отзыв токена добавляет `revoked:access:{hash}` и `revoked:refresh:{hash}` в Redis.
> **AC-12.** Redis ключ `used_refresh:{jti}` использует `SETNX` для предотвращения повторного использования.

### User Story: «Spring Security Configuration»

> **AC-13.** `JwtAuthenticationFilter` извлекает токен из заголовка `Authorization: Bearer {token}` и валидирует его (RS256, claims, TTL).
> **AC-14.** `SecurityConfig` добавляет `JwtAuthenticationFilter` перед `UsernamePasswordAuthenticationFilter`.
> **AC-15.** `@EnableMethodSecurity(prePostEnabled = true)` разрешает использование `@PreAuthorize`.
> **AC-16.** `GET /api/v1/auth/me` защищён и возвращает `200 OK` для валидного токена.
> **AC-17.** `GET /api/v1/admin/users` возвращает `401 Unauthorized` без токена.
> **AC-18.** `GET /api/v1/admin/users` возвращает `403 Forbidden` для обычного пользователя (не ADMIN).
> **AC-19.** `POST /api/v1/admin/users` с ролью ADMIN создаёт пользователя и возвращает `201 Created`.
> **AC-20.** `JwtParser` использует публичный ключ Keycloak для валидации RS256 подписи.
> **AC-21.** При невалидном токене фильтр возвращает `401 Unauthorized` с правильным JSON ошибки.

### User Story: «Интеграция с Platform Service»

> **AC-22.** При успешной аутентификации создается запись в `auth.users` и `platform_service.user_profiles` с связью по `keycloak_user_id`.
> **AC-23.** `GET /api/v1/auth/me` объединяет данные из `auth.users` и `platform_service.user_profiles` через `keycloak_user_id`.
> **AC-24.** В ответе профиля возвращается `verification_status` из `platform_service.user_profiles`.
> **AC-25.** Для SELLER в `auth.users` устанавливается `owner_id`, позволяющий создавать товары.
> **AC-26.** При изменении статуса верификации публикуется событие `platform.user_verified` в Kafka.
> **AC-27.** Кэш профиля в Redis обновляется при изменении данных профиля (TTL: 1 час).

### User Story: «OAuth2 провайдеры»

> **AC-28.** `POST /api/v1/auth/external/link` с валидным access_token и id_token привязывает провайдер к пользователю.
> **AC-29.** `POST /api/v1/auth/external/link` сохраняет данные в `auth.oauth_providers` (provider, provider_id, access_token, refresh_token, expires_at, scopes).
> **AC-30.** `POST /api/v1/auth/external/unlink` удаляет запись из `auth.oauth_providers` и не позволяет отвязать последний провайдер.
> **AC-31.** `GET /api/v1/auth/external/providers` возвращает список всех привязанных провайдеров.
> **AC-32.** При входе через OAuth2 синхронизируются данные из провайдера в `platform_service.user_profiles`.

### User Story: «Кэширование JWT»

> **AC-33.** При каждой валидации токена проверяется Redis на наличие `revoked:access:{token_hash}`.
> **AC-34.** Если токен отозван — возвращается `401 Unauthorized` (нельзя принять отозванный токен через кэш).
> **AC-35.** Кэширование результата проверки revoked (`cache:revoked_check:{hash}`) работает с TTL: 1 минута.
> **AC-36.** При недоступности Keycloak кэшируется публичный ключ для валидации RS256 подписи (TTL: 1 час).
> **AC-37.** При недоступности Keycloak и пустом кэше возвращается `503 Service Unavailable` (не принимаются отозванные токены).

### User Story: «Keycloak Events интеграция»

> **AC-38.** События `auth.user_authenticated`, `auth.user_logout` публикуются Auth Service при вызове API endpoints (`POST /api/v1/auth/login`, `POST /api/v1/auth/logout`).
> **AC-39.** Keycloak Events включены для локального аудита в Keycloak (Events Config → Events Enabled = ON).
> **AC-40.** Документировано, что для полного аудита всех действий (включая Admin Console) можно добавить Kafka Connect Keycloak Source Connector в будущем.

### User Story: «PostgreSQL миграции»

> **AC-41.** Все миграции Liquibase созданы (13 файлов): `users`, `oauth_providers`, `user_profiles`, `roles`, `permissions`, `role_permissions`, `initial_roles`, `indexes`, `audit_logs`, `admin_user`, `avatar_url`, `additional_indexes`.
> **AC-42.** Миграция `03-06-2026-create-table-audit-logs.sql` создана и содержит таблицу `auth.audit_logs` с индексами `idx_audit_logs_user_id`, `idx_audit_logs_event_type`, `idx_audit_logs_created_at`.

### User Story: «Rate Limiting»

> **AC-43.** Для `/api/v1/auth/login`: Redis ключ `rate:login:{ip}:{5min_window}` создаётся и обновляется, при 5-й попытке в течение 5 минут возвращается HTTP 429.
> **AC-44.** Для `/api/v1/auth/external/link`: Redis ключ `rate:link:{user_id}:{10min_window}` создаётся и обновляется, при 3-й попытке в течение 10 минут возвращается HTTP 429.
> **AC-45.** Для `/api/v1/admin/**`: Redis ключ `rate:admin:{user_id}:{1min_window}` создаётся и обновляется, при 10-й попытке в течение 1 минуты возвращается HTTP 429.

### 12.2. Базовые принципы

* **Нет state внутри сервиса** — всё состояние (токены, revoked tokens) хранится в Redis/Keycloak.
* **Использование `@ConfigurationProperties`** — для выноса настроек Keycloak, Redis, Kafka.
* **Тестирование через `@MockBean`** — для портов (`KeycloakPort`, `TokenService`, `PlatformServicePort`).
* **Валидация JWT** — в `JwtAuthenticationFilter`, с обязательным проверкой `audience`, `iss`, `roles`, `exp`, `iat`.
* **JWT Token Service** — центральный компонент для генерации/валидации токенов с алгоритмом RS256, access token (15 мин), refresh token (7 дней, одноразовый).
* **Redis интеграция** — хранение revoked tokens, used refresh tokens, кэш результатов проверки revoked (`cache:revoked_check:{hash}`, TTL: 1 мин), и кэш публичного ключа Keycloak (`cache:public_key`, TTL: 1 час) для ускорения валидации JWT. При недоступности Keycloak и пустом кэше — возврат `503 Service Unavailable`.
* **Kafka события** — Auth Service публикует события `auth.user_authenticated`, `auth.user_logout` при вызове API endpoints (`POST /api/v1/auth/login`, `POST /api/v1/auth/logout`). Для полного аудита (включая Admin Console) можно добавить Kafka Connect Keycloak Source Connector в будущем.
* **Platform Service интеграция** — синхронизация `auth.users` ↔ `platform_service.user_profiles` через `keycloak_user_id`.
* **Spring Security** — фильтр `JwtAuthenticationFilter` для валидации токенов, `@EnableMethodSecurity` для аннотаций `@PreAuthorize`, настройка защищённых endpoints.
* **JwtParser** — парсер JWT токенов с RS256 подписью через публичный ключ Keycloak. Кэширует публичный ключ (TTL: 1 час) и результаты проверки отозванных токенов (TTL: 1 мин) для производительности.

## 13. Критические риски и mitigation

| Риск | Описание | Уровень | Mitigation |
|------|----------|---------|------------|
| **Высокий** | Зависимость от Keycloak для входа | Высокий | 1. Внедрить локальный кэш успешных аутентификаций (TTL 5 мин) в Redis. <br> 2. Убедиться, что `refresh_token` валиден даже при оффлайне Keycloak (если не использован в кэше). |
| **Средний** | Рост Redis-памяти из-за большого количества `revoked:access:{hash}` | Средний | Настроить автоматический `EXPIRE` (15 мин) для `revoked:access:...`, и 7 дней для `revoked:refresh:...`. |
| **Средний** | Нарушение согласованности при повторной отправке `refresh_token` | Средний | Использовать Redis `SETNX` (SET if Not eXists) при попытке использовать `refresh_token`. |
| **Низкий** | Утечка `access_token` через логи | Низкий | Фильтровать все логи через `MDC` и `SecurityLoggingFilter`, заменять `Authorization` на `***`. |

Это техническое задание определяет **полный функционал MVP Auth Service**, необходимый для обеспечения безопасного входа пользователей, интеграции с API Gateway, Platform Service и поддержки OAuth2 провайдеров.

Сервис **должен быть разработан с нуля**, соответствовать требованиям к безопасности и масштабируемости, и быть готов к интеграции в существующую инфраструктуру после завершения всех этапов разработки и тестирования.

Утверждённое ТЗ служит основой для планирования спринта, расчёта трудозатрат и приёмки результата.
