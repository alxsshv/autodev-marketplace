# План создания учебного плана для AutoDev Marketplace

## Цель
Создать детальный учебный план (`docs/study_plan.md`) для Java backend-разработчика, который позволит освоить современные практики разработки микросервисов через практическое создание системы продажи автозапчастей.

## Фаза 1: Понимание требований

### Выполненные действия
- Прочитан архитектурный обзор системы из `docs/architecture/system-overview.md`
- Прочитаны указания для роли ментора из `docs/roles/mentor.md`
- Проанализирована структура проекта с помощью `find_files`
- Обнаружен существующий сервис `api-gateway` в `services/api-gateway/`
- Созданы вспомогательные документы:
  - `docs/learning-resources.md`
  - `docs/coding-standards.md`
  - `docs/test-cases.md`
  - `docs/dev-environment.md`

### Ключевые выводы
1. Проект использует микросервисную архитектуру на Spring Boot 3 и Java 17
2. Уже реализован API Gateway на Spring Cloud Gateway
3. Используется Gradle как система сборки
4. Архитектура включает 12 микросервисов, перечисленных в системном обзоре
5. Требуется итеративный подход к обучению, начиная с простых сервисов

## Фаза 2: Проектирование учебного плана

### Структура учебного плана
План будет включать следующие разделы:

1. **Введение**
   - Цели обучения
   - Ожидаемые результаты
   - Продолжительность (13 недель)
   - Формат взаимодействия

2. **Подготовительный этап**
   - Настройка окружения
   - Настройка CI/CD
   - Правила работы с Git

3. **Укрупнённый план**
   - Порядок разработки сервисов

4. **Детализированный план по микросервисам**
   - Для каждого сервиса: задачи, технологии, критерии приёмки

5. **Оценка прогресса**
   - Чек-листы
   - Тесты
   - Итоговый проект

6. **Дополнительные ресурсы**
   - Ссылки на документацию
   - Сообщества

### Порядок разработки микросервисов
На основе архитектурного обзора, зависимостей между сервисами и вашего замечания, предлагаю следующий порядок разработки:

1. **Service Discovery** - централизованное обнаружение сервисов (Consul)
2. **Auth Service** - централизованная аутентификация
3. **User Service** - управление пользователями
4. **Catalog Service** - каталог товаров
5. **Pricing & Inventory Service** - цены и наличие
6. **Search Service** - поиск по VIN и артикулам
7. **API Gateway** - уже частично реализован, требует доработки
8. **Order Service** - оформление заказов
9. **Notification Service** - уведомления
10. **Review Service** - отзывы
11. **Recommendation Service** - рекомендации
12. **Admin Service** - администрирование
13. **Analytics & Reporting Service** - аналитика

### Обоснование порядка
1. Начинаем с Service Discovery, так как он необходим для динамического обнаружения всех последующих сервисов
2. Затем Auth и User Service, так как они являются фундаментальными для всей системы
3. Далее Catalog и Pricing, так как они предоставляют основные бизнес-данные
4. Search Service зависит от Catalog
5. API Gateway интегрируется со всеми сервисами и использует Service Discovery
6. Order Service зависит от Catalog, Pricing и User
7. Notification Service используется всеми сервисами
8. Review и Recommendation Service зависят от данных о пользователях и товарах
9. Admin и Analytics Service - завершающие, используют данные из всех сервисов

## Фаза 3: Проверка и уточнения

### Вопросы для пользователя
1. Согласны ли вы с предложенным порядком разработки микросервисов?
2. Есть ли предпочтения по конкретным технологиям для реализации определённых сервисов?
3. Какой объём работы на каждую итерацию считаете оптимальным (1 сервис в неделю, 2 сервиса в неделю и т.д.)?
4. Нужно ли включить в план обучение по Kubernetes, или ограничиться Docker Compose?

## Фаза 4: Финальный план

После получения ответов на вопросы, я:
1. Создам полный учебный план в `docs/study_plan.md`
2. Включу в него все запрошенные разделы
3. Добавлю примеры кода и диаграммы для ключевых этапов
4. Уточню критерии приёмки для каждой задачи
