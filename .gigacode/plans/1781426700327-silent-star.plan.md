# Архитектурный аудит документации auth-service

**Дата:** 2026-06-14  
**Аудитор:** GigaCode  
**Цель:** Оценка качества, согласованности и полноты документации для передачи аналитику

---

## Выявленные проблемы

### 1. Критические противоречия

| Проблема | Документы | Описание | Влияние на ТЗ |
|---------|-----------|----------|---------------|
| master.xml vs master.yaml | database-migrations.md, data-model.md, roadmap.md | Некоторые документы используют XML формат, другие YAML | Разработчик может создать неправильную структуру миграций |
| Отсутствие /sync endpoint | api-specification/auth-service.yaml | В документации нет описания `/api/v1/auth/sync` endpoint, но он используется в user-registration-architecture.md для webhook от Keycloak | Аналитик не сможет понять, какие endpoints существуют в auth-service |
| Описания webhook событий | user-registration-architecture.md, kafka-events/auth-service-events.md, communication-policy.md | Разные форматы описания событий Keycloak (USER_CREATED vs user_created) | Разработчик может неправильно настроить webhook конфигурацию |

### 2. Пробелы в документации по Kafka событиям

| Проблема | Документ | Описание |
|---------|----------|----------|
| Отсутствие спецификации payload | kafka-events/auth-service-events.md | Нет строго определенных схем JSON для каждого события |
| Отсутствие DLQ конфигурации | kafka-events/auth-service-events.md | Описана концепция DLQ, но нет конкретной конфигурации |
| Отсутствие примеров событий для platform-service | kafka-events/auth-service-events.md | Нет описания событий, которые генерирует platform-service |

### 3. Сложность sequence diagrams

| Проблема | Документ | Описание |
|---------|----------|----------|
| Избыточная сложность | sequence-diagrams/auth-register.md | Слишком много сценариев в одном документе,难 понять основной flow |
| Отсутствие простой диаграммы | sequence-diagrams/auth-register.md | Нет простой базовой диаграммы для быстрого понимания |

### 4. Проблемы в документации по безопасности

| Проблема | Документ | Описание |
|---------|----------|----------|
| Повторение одних и тех же разделов | security-strategy.md, security/rbac.md, system-overview.md | Роли и JWT структура описаны 3-4 раза с одинаковым содержанием |
| Отсутствие единого источника правды | security/rbac.md | Нет четкого указания, какие endpoints требуют какие роли |
| Неполное описание revoked tokens | security/revoked-tokens.md | Нет описания того, как это влияет на API endpoints |

### 5. Несогласованность миграций

| Проблема | Документы | Описание |
|---------|-----------|----------|
| master.xml vs master.yaml | database-migrations.md (использует master.xml), data-model.md (использует master.yaml) | Противоречие в рекомендованных форматах |
| Отсутствие миграции v1.1.0 | data-model.md | Упомянута миграция v1.1.0 для таблицы revoked_tokens, но она удалена из реализации |

## Приоритетные действия

### Критические (должны быть исправлены перед передачей аналитику)

1. **Устранить противоречия master.xml vs master.yaml**
   - Выбрать один формат (рекомендуется YAML)
   - Обновить все документы

2. **Добавить /sync endpoint в OpenAPI спецификацию**
   - Описать endpoint для webhook от Keycloak
   - Указать формат входных данных

3. **Единый формат webhook событий Keycloak**
   - Установить snake_case и строчные буквы как стандарт
   - Обновить все документы

4. **Создать единую спецификацию Kafka событий**
   - Определить строгие JSON схемы для каждого события
   - Описать DLQ конфигурацию

### Важные (рекомендуется исправить перед передачей аналитику)

5. **Упростить sequence diagrams**
   - Создать простую базовую диаграмму
   - Вынести сложные сценарии в отдельные документы

6. **Устранить дублирование безопасности**
   - Выбрать один основной документ (security-strategy.md)
   - Ссылаться на него из других документов

7. **Описать RBAC endpoints**
   - Указать для каждого endpoint, какие роли требуются
   - Создать таблицу соответствия endpoints ↔ роли

8. **Обновить миграции**
   - Убрать упоминания удаленной таблицы revoked_tokens
   - Уточнить структуру master changelog
