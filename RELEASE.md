# Руководство по релизам и ветвлению

> Действует для монорепозитория `autodev-marketplace`.
> Каждый микросервис релизится **независимо**.

---

## 1. Общие правила

| Правило | Описание |
|---------|----------|
| **Основная ветка разработки** | `develop` — сюда сливаются все Pull Request'ы |
| **Production** | `main` — только стабильный код из релизных веток |
| **Никаких прямых пушей** | В `main` и `develop` — только через Pull Request |
| **Версионирование** | [SemVer](https://semver.org/lang/ru/): `MAJOR.MINOR.PATCH` |
| **Реестр образов** | Docker Hub (публичные репозитории) |

---

## 2. Типы веток

### 2.1. Feature-ветки
Формат: `feature/<service>-<краткое-описание>`

Примеры:
```
feature/api-gateway-oauth2
feature/service-b-payment-retry
```

- Отводятся от `develop`
- После завершения — PR в `develop`
- CI запускает тесты **только для изменённого сервиса** (paths-filter)

---

### 2.2. Релиз одного сервиса
Формат: `release/<service>/v<версия>`

Примеры:
```
release/api-gateway/v2.1.0
release/service-b/v1.0.3
```

- Отводятся от `develop`
- Содержат только изменения одного сервиса
- При пуше CI автоматически:
  1. Собирает `bootJar` с указанной версией
  2. Собирает Docker-образ
  3. Публикует в Docker Hub: `yourname/<service>:<версия>` + `yourname/<service>:latest`
  4. Создаёт git-тег: `<service>/v<версия>` (например, `api-gateway/v2.1.0`)
- После успешной сборки — PR в `main`, затем PR в `develop` (чтобы теги и версии синхронизировались)

> **Важно:** имя сервиса в ветке должно совпадать с именем папки в `services/` и именем репозитория на Docker Hub.

---

### 2.3. Batch-релиз (платформенный)
Формат: `release/batch/v<ГГГГ.ММ.ДД>`

Примеры:
```
release/batch/v2026.08.05
release/batch/v2026.08.15
```

Используется, когда:
- Изменился `shared-lib` и нужно пересобрать **несколько** зависимых сервисов
- Выпускается координированное обновление платформы

При пуше CI:
1. Автоматически определяет, какие сервисы изменились с момента последнего релиза `main`
2. Собирает и публикует образы **только для изменённых сервисов**
3. **Не создаёт git-теги** (создайте вручную, если нужно)

---

### 2.4. Hotfix
Формат: `hotfix/<service>/v<версия>`

Примеры:
```
hotfix/api-gateway/v2.1.1
hotfix/service-b/v1.0.4
```

- Отводятся от `main`
- Исправляют критический баг на production
- После пуша CI собирает и публикует образ с новой версией
- Обязательно: PR в `main` **и** PR в `develop` (чтобы фикс не потерялся)

---

## 3. Порядок релиза (пошагово)

### Релиз одного сервиса

```bash
# 1. Убедитесь, что develop актуален
git checkout develop
git pull origin develop

# 2. Создайте релизную ветку
git checkout -b release/api-gateway/v2.1.0

# 3. (Опционально) Обновите версию в build.gradle.kts сервиса
#    Или передавайте версию через -PreleaseVersion=2.1.0 в CI

# 4. Запушьте ветку — CI начнёт сборку автоматически
git push origin release/api-gateway/v2.1.0
```

**Что происходит дальше:**
1. GitHub Actions собирает `services/api-gateway`
2. Публикует образы:
    - `docker pull yourname/api-gateway:2.1.0`
    - `docker pull yourname/api-gateway:latest`
3. Создаёт git-тег `api-gateway/v2.1.0`
4. Вы создаёте PR `release/api-gateway/v2.1.0` → `main`
5. После мержа в `main` — опционально PR `main` → `develop`

---

## 4. Версионирование: когда какой номер

| Изменение | Версия | Пример |
|-----------|--------|--------|
| Исправление бага, оптимизация | PATCH | `2.1.0` → `2.1.1` |
| Новая функциональность, обратно совместимая | MINOR | `2.1.0` → `2.2.0` |
| Ломающие изменения API, мажорный рефакторинг | MAJOR | `2.1.0` → `3.0.0` |

---

## 5. Docker Hub: где брать образы

После релиза образы доступны по адресам:

```bash
# Конкретная версия (рекомендуется для production)
docker pull yourname/api-gateway:2.1.0

# Последняя стабильная (для разработки, НЕ для production)
docker pull yourname/api-gateway:latest
```

> **В production используйте только строгие версии** (`:2.1.0`), никогда `latest`.

---

## 6. Частые ошибки

| Ошибка | Последствие |
|--------|-------------|
| `release/api-gateway/v2.1.0` — сервис не совпадает с папкой в `services/` | CI не найдёт модуль, сборка упадёт |
| Забыли создать PR `hotfix` → `develop` | Фикс пропадёт при следующем релизе |
| Используете `latest` в Kubernetes/Compose | Откат невозможен, непредсказуемое поведение |
| Пушите в `release/batch/` без изменений в сервисах | CI не соберёт ничего, пустой прогон |

## 7. Схема ветвления (кратко)

```
develop  ●────●────●────●────●────●────●────●
         ↑    ↑    ↑    ↑         ↑    ↑
         │    │    │    │         │    └─ PR hotfix/... → develop
         │    │    │    │         │
         │    │    │    │         └─ PR main → develop (после релиза)
         │    │    │    │
feature  ●────●────┘    │         release/api-gateway/v2.1.0
feature/service-b-...    │              │
                         │              ▼
main                     ●────────────●
                              ↑
                              └─ PR release/api-gateway/v2.1.0 → main

hotfix/api-gateway/v2.1.1
       │
       ▼
main   ●────●
       ↑
       └─ PR hotfix → main, затем hotfix → develop
```

## 8. Полезные команды

```bash
# Посмотреть последние релизные теги
git tag -l "*gateway*" --sort=-v:refname

# Удалить локальную релизную ветку после мержа
git branch -d release/api-gateway/v2.1.0

# Протестировать сборку локально (без пуша)
./gradlew :services:api-gateway:bootJar -PreleaseVersion=2.1.0
```
